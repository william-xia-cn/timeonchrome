## Goal

建立独立的任务管理产品模型，用一次性任务表示一件必须通过 Chrome 完成的事情。任务到达计划开始时间后形成持续存在的强制使用义务，直到累计完成要求的有效任务使用时长、收到可信完成事实或被授权取消。

任务管理必须独立于日历例程配置，但在运行时具有更高的内容约束优先级。任务不永久修改网站分类，不改变时间的统计性质，也不绕过配额、安全规则或黑名单。

## Problem

固定时间窗口无法准确表达以下任务场景：

- 任务计划 09:00 开始，但孩子 10:00 才打开 Chrome；
- 使用一段时间后关闭 Chrome，剩余任务应在下次打开时继续；
- 任务暂停后停止进度，恢复后继续完成剩余时长；
- 多个未完成任务同时存在，需要在各自资源之间切换；
- 外部学习系统未来可以提供更精确的开始、暂停、进度和完成事实；
- 任务完成应立即解除限制，而不是等待固定自然时间结束。

把这些行为继续表达为固定时间例程，会混淆自然时间窗口和必须完成的任务进度。任务应成为独立对象，并以有效使用时长而不是固定截止时间作为完成依据。

## Core Definitions

### 任务

任务是一件一次性的、必须通过 Chrome 完成的强制使用目标。第一版任务由计划开始时间、要求有效使用时长和允许资源组成，不支持周期重复。

### 计划开始时间

计划开始时间是任务最早进入强制状态的自然时间。到达该时间后，任务即使尚未打开 Chrome，也会保持为未完成义务；之后任何一次 Chrome 使用都必须先遵守生效任务的内容范围。

### 要求有效使用时长

要求有效使用时长是任务必须累计完成的 Chrome 有效任务使用时间，不是自然时间跨度。配置范围为 1 分钟至 24 小时。以下条件同时满足时才累计：

- Chrome 处于前台；
- 系统不是 idle 或 locked；
- 存在当前活动标签页；
- 当前网页属于该任务允许资源；
- 任务处于强制执行中而不是暂停状态。

Chrome 关闭、失焦、系统空闲、停留在非任务页面或任务暂停时不累计任务进度。

### 已完成和剩余时长

已完成时长是已经可靠累计到该任务的有效使用时间。剩余时长等于要求时长减去已完成时长，最小为零。同一使用时间不得重复累计到同一个任务。

### 预计结束时间

预计结束时间只是在任务持续执行且不中断条件下，由当前时间和剩余时长派生的展示值。它不是固定截止时间，不是任务配置真值，也不能使未完成任务自动失效。

### 任务允许资源

任务只允许配置明确资源集合：域名、URL 和已支持的任务资源对象。同一任务内的资源取去重并集。任务只限制允许访问的内容，不改变资源原有网站性质。

- 第一版不支持按访问管理分类创建任务资源，不允许选择学习网站、复合网站、受限娱乐网站或黑名单网站这类类型级范围；
- 域名资源覆盖该域名自身及其所有子域；填写具体子域时只覆盖该子域范围，不扩大到兄弟子域；
- URL 资源必须明确选择“精确页面”或“路径范围”：精确页面保留业务 query，路径范围忽略 query 并只覆盖相同 host 下的同一路径边界及子路径；
- URL 规范化忽略 hash、尾斜杠差异和常见 tracking 参数；
- YouTube 视频、播放列表和频道由粘贴 URL 自动识别为任务资源对象，不要求用户手写对象类型；
- 受限娱乐网站和未归类网站如需纳入任务，只能作为明确域名、URL 或任务资源对象加入；
- 黑名单对象不能加入任何任务资源；黑名单校验属于任务命中后的基础安全阻断，任务本身不能穿透；
- 同一资源在多个任务中出现时，只形成一个当前允许对象，不重复放行、落账或扣减配额。

### 任务核心字段冻结

任务名称、计划开始时间、要求有效使用时长和允许资源构成任务核心字段。任务到达计划开始时间或已经产生有效进度后，核心字段冻结；如需调整，家长应取消原任务并创建新任务。暂停、恢复、人工完成和取消属于生命周期动作，不视为修改核心字段。

### 进度归属顺序

当前页面同时命中多个生效任务时，每一自然秒只能归属一个任务。归属顺序固定为：

1. 原计划开始时间较早的任务；
2. 计划开始时间相同，则比较规范化后的任务名称；
3. 名称仍相同，则比较任务 ID。

该顺序只决定进度归属，不改变所有生效任务资源取并集的访问规则。

### 多设备进度

任务属于 profile，而不是单台设备。同一 profile 的多台设备可以产生任务有效使用区间；云端按区间并集累计，同一自然秒最多计入一次。设备本地只使用最后一次云端确认进度和本机尚未上传的有效区间进行保守判断，不能因为无法看到其他设备的未同步进度而提前完成任务。

### 任务完成事实

任务可以通过本地可靠累计的有效任务使用时长达到要求，或授权外部来源明确报告 `completed` 而完成。任务完成后立即退出强制集合；外部完成事实可以让任务在本地要求时长耗尽前提前完成。

## Scope

This spec includes:

- 一次性任务的核心产品定义；
- 计划开始、强制执行、暂停、恢复、完成和取消行为；
- 有效任务使用时长、已完成时长和剩余时长；
- 多任务并行时的允许资源与进度归属；
- 任务与日历例程、基础场景、网站性质、配额和安全规则的关系；
- 未来授权外部来源补充任务事实的产品边界；
- 功能验收标准和后续实现必须覆盖的测试场景。

## Out Of Scope

This spec does not include:

- 周期任务或周期任务实例生成器；
- 固定截止时间、逾期后自动失效或跨周期积压规则；
- 日历例程的创建、冲突和一次性覆盖规则；
- 任务 schema、storage key、数据库表或 migration；
- Worker API、外部事件认证协议、同步和离线冲突解决方案；
- 任务提醒、通知、完成证明或家长确认的具体 UI；
- Pages、Popup、本地 Admin 的具体视觉稿和组件布局；
- 对当前代码、API、数据库或运行逻辑的任何修改。

## User Behavior

### 创建和生效

- 家长创建一次性任务，设置计划开始时间、要求有效使用时长和允许资源。
- 要求有效使用时长必须在 1 分钟至 24 小时之间。
- 第一版不提供周期重复选项。
- 到达计划开始时间后，任务进入强制执行状态。
- 如果创建任务时计划开始时间已经过去，任务保存成功后立即进入强制执行状态。
- Chrome 未打开时任务不累计进度，但任务不会消失或自动完成。
- 任务可以跨自然日持续存在，直到完成、暂停或被授权取消。
- 任务到达计划开始时间或产生进度后，名称、计划开始时间、要求时长和允许资源不可再编辑；修改需求通过取消并新建任务处理。

### 强制内容范围

- 只要存在强制执行中的未完成任务，Chrome 可用内容就收窄为所有此类任务允许资源的去重并集。
- 日历例程中未被任务选中的资源暂时不可使用。
- 当前网页不属于任务资源并集时，系统应提醒或阻断。
- 所有强制任务完成、暂停或取消后，系统恢复当前生效的日历例程；没有日历例程时恢复基础场景。

运行优先级固定为：

`未完成任务内容约束 > 原访问管理流程（网站事实、黑名单、安全、配额、日历例程/旧时间段和基础场景）`

这里的任务优先级只控制“当前必须使用任务资源”的内容范围：有生效任务且当前页面不是任务资源时，由 Task 独立模块阻断；当前页面命中任务资源时，Task 不附加任何放行或绕过标志，原访问管理流程从头按现有规则继续执行。任务资源仍可能被黑名单、安全、配额或时间段阻断。

### 任务进度

- 任务进度只来自满足有效使用条件的任务网站使用事实。
- 当前网站只属于一个生效任务时，仅累计该任务。
- 当前网站同时属于多个生效任务时，按“原计划开始时间、规范化任务名称、任务 ID”的稳定顺序只累计一个未完成任务。
- 最早任务完成后，相同资源的后续使用可以累计到下一个匹配任务。
- 多任务资源并集不能造成同一秒钟重复计时或重复扣减配额。
- 停留在任务允许资源不等于持续有效使用；Chrome 失焦或系统 idle 后应停止累计。

### 暂停和恢复

- 任务只能由家长或授权外部来源暂停和恢复，孩子不能自行暂停强制任务。
- 暂停后立即停止累计该任务进度，并将该任务移出生效资源集合。
- 若仍有其他任务强制执行，继续使用剩余任务资源并集。
- 若没有其他任务强制执行，恢复当前日历例程或基础场景。
- 恢复后按原剩余时长继续执行，不重新开始，也不因暂停自然时间而减少剩余时长。

### 完成和取消

- 本地累计达到要求时长后，任务立即完成并退出生效资源集合。
- 家长可以留痕地提前完成任务；完成来源必须可审计，不能伪装为自然累计完成。
- 授权外部来源报告明确完成事实时，任务可以提前完成。
- 家长或授权外部来源取消任务后，任务立即退出生效资源集合并保留取消状态。
- 已完成和已取消任务作为不可删除历史记录保留，默认可折叠展示。
- 完成和取消都必须触发当前网页重新评估。
- 不存在“提前完成但继续限制到固定结束时间”的行为。

### 外部事实补充

- 外部系统不是另一套任务机制，也不直接下发网站放行规则。
- 没有外部接入时，本地机制必须能够独立完成任务强制、进度累计和完成判断。
- 未来外部来源可以补充实际开始、暂停、恢复、进度和完成事实。
- 外部进度必须作为幂等状态快照或校准事实处理，不能与本地进度直接相加造成重复累计。
- 外部事件只有通过授权和任务身份校验后才能改变任务状态。

### 网站性质与配额

- 任务不改变网站的永久分类或使用性质。
- 学习、复合、受限娱乐和未归类网站继续按各自现有性质计时、扣减配额和进入归类流程。
- 配额耗尽时继续执行现有配额规则；任务保持未完成，不自动赠送或借用配额。
- 黑名单、安全规则和其他不可覆盖限制始终优先，不能被任务允许资源穿透。

## Data And State

本规格只定义概念状态，不指定持久化字段：

- 计划：尚未到达计划开始时间；
- 强制执行中：已到开始时间、未完成、未暂停且未取消；
- 已暂停：停止进度并退出生效资源集合；
- 已完成：本地要求时长已满足或收到授权完成事实；
- 已取消：由家长或授权外部来源终止；
- 任务进度：要求有效时长、已完成时长、剩余时长；
- 当前任务上下文：一个或多个强制任务、允许资源并集和当前进度归属任务。

任务状态、任务进度和当前访问约束必须能够分别表达。预计结束时间只能作为运行时展示值，不能持久化为使任务自动失效的固定截止事实。

持久生命周期只包含 `open / paused / completed / cancelled`。用户可见的“计划中”和“强制执行中”由 `open`、计划开始时间与当前时间派生，不作为独立持久状态。任务开始、产生进度、暂停、恢复、完成或取消均必须保留 revision 或事件证据，供并发控制和审计使用。

## Acceptance Criteria

1. 产品界面和文档只使用“任务”作为该功能的正式名称。
2. 第一版只能创建一次性任务，不提供周期任务。
3. 任务以计划开始时间和要求有效使用时长为核心，不配置固定截止时间。
4. 到达计划开始时间后，未完成任务在每次 Chrome 使用时持续强制任务资源范围。
5. Chrome 关闭、失焦、idle、非任务页面和任务暂停期间不累计任务进度。
6. 任务可以跨自然日保持未完成，并从原剩余时长继续。
7. 多个强制任务的允许资源按去重并集生效。
8. 同一资源命中多个任务时，按原计划开始时间、规范化任务名称、任务 ID 的稳定顺序只累计一个未完成任务。
9. 任务累计完成或收到授权完成事实后立即解除该任务限制。
10. 只有家长或授权外部来源能够暂停、恢复或取消任务。
11. 外部系统缺失或不可用时，本地任务机制仍可完整运行。
12. 任务不会改变网站性质、使用性质或配额归属。
13. 配额耗尽不会因任务而自动放行，任务保持未完成。
14. 黑名单和不可覆盖规则不能被任务绕过。
15. 任务状态变化和资源集合变化会重新评估当前网页，且不造成重复计时或重复扣减。
16. 要求有效使用时长只能配置为 1 分钟至 24 小时。
17. 任务开始或产生进度后，核心字段冻结；家长只能执行暂停、恢复、留痕完成或取消。
18. 完成和取消任务保留为不可删除历史记录。
19. 第一版任务资源只接受明确域名、URL 和任务资源对象，不接受访问管理分类作为资源。
20. 命中任务资源时只通过 Task 内容约束，随后继续执行原时间段限制；网站性质、统计性质和配额来源保持不变。
21. 多设备重叠的有效使用区间按并集累计，同一自然秒最多计入一次。
22. 只有当前档案所有受管在线设备都报告 `taskManagementV1` capability 时，Pages 才允许创建任务。
23. 域名资源覆盖自身与子域；URL 资源按显式的精确页面或路径范围规则匹配，扩展与 Worker 必须使用同一 canonical 结果。

## Required Tests

- Unit: 任务状态转换、有效进度累计、暂停/恢复、跨日剩余时长、多任务资源并集和稳定进度归属顺序。
- Integration: 任务强制范围与网站分类、日历例程、配额检查、idle/focus 边界和当前网页重评估的组合行为。
- E2E: 延迟打开 Chrome、分段完成、跨日继续、暂停恢复、单任务、多任务重叠、提前人工/外部完成、配额耗尽和旧设备 capability 阻断。
- Manual: 家长创建、暂停、恢复、留痕完成和取消任务，查看剩余时长、当前强制任务、有效资源摘要和不可删除历史。
- Release gate: 由后续实现设计确定；本规格不定义发布版本或发布门禁。

## Release Risk

Known release risks:

- 若任务时长按自然时间而不是有效使用时间累计，关闭 Chrome 或空闲可能错误完成任务。
- 若孩子能够直接暂停任务，强制策略可能被绕过。
- 若同一使用时间累计到多个任务，任务进度会被重复兑现。
- 若任务重新解释网站性质，可能破坏统计和配额口径。
- 若任务完成或暂停后没有重检当前网页，旧限制或旧放行可能继续生效。
- 若外部进度与本地进度直接相加，可能产生重复累计和提前完成。

## Rollback Risk

Rollback concerns:

- 任务状态和进度一旦同步到云端，旧客户端必须忽略未知字段而不能损坏现有配置。
- 若任务身份或进度进入用量账本，回滚时必须保留历史事实，不得按当前任务状态重算。
- 外部完成事实必须保留来源和幂等身份，回滚不能使已完成任务重新进入强制状态。

## Handoff Requirements

本规格和独立技术设计已由 Product Owner 批准为 Approved。Build&Test 进入代码实现前必须先完成以下隔离闸门：

1. 由 Product Owner 选择并整理当前工作区已有改动；
2. 确认 `git status` 干净；
3. 执行 `git fetch origin` 并确认本地 `master` 与最新远端基线一致；
4. 创建并使用 `codex/task-management-v1`；
5. 任务代码、migration 和测试不得与其他功能提交混合。

Build&Test must report:

- changed files
- behavior changes
- tests run and results
- known risks
- scope conformance audit
- out-of-scope confirmation

Product&Project Mg must review conformance before releaseMg acceptance.
